# Grok Bot 风格 UI 设计规范 · Pi Agent V2.0

**定位：** 活在 Obsidian 中、面向普通使用者的 AI 助手通讯录  
**设计目标：** 在视觉、布局、比例、组件和交互上高度接近用户提供的 Grok Bot 界面  
**适用平台：** Obsidian 桌面主工作区、笔记旁侧栏、Android、iPhone、插件设置页  
**版本日期：** 2026-10-22

**设计北极星：像打开通讯软件一样，找到助手、说清任务、读到结果。功能可以复杂，界面保持轻盈。**

本规范依据用户提供的 [Grok Bot 风格 UI 设计规范 V1.0](references/GROKBOT-UI-V1.md) 和本聊天中的桌面、手机截图重写。参考文档不是已核实的 Grok Bot 官方设计系统；下列色值、尺寸、字体和时长是本项目的设计目标，不声称为官方测量值，也不表示当前代码已全部实现或达到目标。

本文规定长期设计标准；`DESIGN.md` 记录各轮设计决定，`VALIDATION.md` 记录实际验收。电脑预览、接管、邮件卡片、表情反馈等尚未实现的内容仅规定未来设计方式，不构成本轮新增功能要求，不显示无效入口。本次重写只修改文档。

## 01. 整体设计风格

### 核心视觉

采用极简、现代、轻量的设计语言。

关键词：

- Minimal / 极简
- Soft UI / 轻柔界面
- Neutral / 中性色
- Rounded / 圆润
- Spacious / 大面积留白
- Subtle Motion / 微动效
- Conversational / 对话式交互

视觉特征：

1. 整体以白色、近白色、浅灰色、黑色为基础。
2. 不使用大面积彩色背景或夸张渐变。
3. 通过留白、文字权重和层级组织信息。
4. 按钮、输入框和消息气泡采用较大的圆角。
5. 边框极浅，阴影柔和，尽量减弱容器的存在感。
6. 彩色主要来自 Bot 头像及少量状态反馈。
7. 界面要轻盈、安静、精致，避免传统后台系统那种厚重感。

**核心要求：宁愿减少装饰，也不要用视觉噪声填充空白。**

视觉相似度先看通讯录、聊天和输入区的整体结构与比例，再看色彩和细节。不能只把按钮改圆就认为完成还原。一个区域突出一个主要动作，常用操作直接到达，技术配置按需出现。

## 02. 色彩规范

下列色板是默认中性主题目标。使用 Obsidian 自定义主题时，通过插件语义变量映射宿主颜色，保留表面层级、消息对比与可读性，不在组件内散落固定色值，不改动宿主全局样式。

### Light Theme — 默认浅色主题

| Token | HEX | 使用位置 |
|---|---|---|
| Background | `#FAFAFA` | 应用背景 |
| Canvas | `#FFFFFF` | 聊天主画布 |
| Surface | `#F5F5F5` | 消息气泡、卡片 |
| Surface Hover | `#EEEEEE` | 悬停背景 |
| Surface Active | `#EAEAEA` | 选中项目 |
| Text Primary | `#151515` | 标题、正文 |
| Text Secondary | `#858585` | 说明、摘要 |
| Text Tertiary | `#B7B7B7` | 非关键弱化信息的色板起点，需检查可读性 |
| Border | `#E8E8E8` | 极浅分割线 |
| Border Strong | `#DADADA` | 输入框激活边框 |
| User Bubble | `#111111` | 用户消息 |
| User Text | `#FFFFFF` | 用户消息文字 |

### Dark Theme — 深色主题

| Token | HEX |
|---|---|
| Background | `#101010` |
| Canvas | `#141414` |
| Surface | `#202020` |
| Surface Hover | `#2B2B2B` |
| Surface Active | `#343434` |
| Text Primary | `#F5F5F5` |
| Text Secondary | `#A0A0A0` |
| Text Tertiary | `#777777`，需检查可读性 |
| Border | `#303030` |
| Border Strong | `#555555` |
| User Bubble | `#ECECEC` |
| User Text | `#141414` |

### 功能色

- 活动中：`#8B5CF6`，紫色，用于真实工作状态的小型标记。
- 完成：`#35A76D`，绿色。
- 等待确认：`#E7A04B`，琥珀色。
- 错误：`#E25D5D`，柔和红色。

功能色不得成为页面主背景色。角色色不自动染色正文、联系人名称或设置标题；普通主操作保持中性。错误必须同时提供图标或文字，不只显示红点。

`Text Tertiary #B7B7B7` 是色板起点，对比偏低，不能直接用于必须读清的时间、占位符、说明和按钮文字。实际背景上读不清时改用 Secondary 或加深；深色主题的弱化信息同样以实际可读性为准。

现有 `--pi-canvas`、`--pi-ink`、`--pi-secondary`、`--pi-bubble` 分别承接画布、主文字、辅助文字、助手表面语义。其余 Token 先查现有变量，确需增加时集中定义，桌面与手机复用；表中名称不表示同名 CSS 变量已经存在。

## 03. 字体系统

### 字体建议

英文字体：

`Inter, -apple-system, BlinkMacSystemFont, "SF Pro Text", sans-serif`

中文字体：

`PingFang SC, Noto Sans SC, Microsoft YaHei, sans-serif`

采用视觉接近的系统无衬线方案，不把未经核实的字体家族或更换历史写成官方事实。插件优先使用宿主 `--font-interface` 与系统回退，Inter 仅在已安装时使用，不为相似度额外下载字体。

### 字号与字重

| 元素 | 字号 | 字重 | 行高 |
|---|---:|---:|---:|
| 页面大标题 | 28px | 600 | 1.25 |
| 页面标题 | 22px | 600 | 1.3 |
| Bot 名称 | 15px | 600 | 1.4 |
| 主聊天正文 | 15–16px | 400 | 1.55 |
| 普通按钮 | 14px | 500 | 1.4 |
| 侧边栏名称 | 14px | 500 | 1.4 |
| 侧边栏摘要 | 12–13px | 400 | 1.4 |
| 时间标签 | 12px | 400 | 1.4 |
| 辅助说明 | 12–13px | 400 | 1.5 |

文字默认左对齐。

减少全大写标题，不使用过粗或过密的字体。优先用轻微字重差异建立层级。

上述尺寸使用 CSS 像素，不按截图物理像素照搬。手机输入文字保持 16px；现有紧凑聊天正文可保持 15px，其他正文通常 15–16px，行高 1.55–1.65。放大阅读时允许布局增长，不用压小字体解决溢出。

Markdown 保留标题、列表、代码与引用语义，但标题控制在聊天尺度，不继承宿主巨大标题。长路径和模型 ID 可断行；代码块、宽表格在自身区域横向滚动，不撑破整页。

## 04. 页面布局系统

### Desktop 页面结构

默认以 `1440 × 900` 为设计基准。

宽屏参考结构如下；右侧区域是可选扩展，不要求当前插件新增第三栏：

**左侧 Bot Sidebar + 中央 Chat Workspace + 可选右侧 Detail / Computer Panel**

| 区域 | 推荐尺寸 |
|---|---|
| 左侧边栏 | 280px |
| 顶部标题栏 | 56px |
| 主聊天区 | 剩余宽度自适应 |
| 聊天正文最大宽度 | 820px |
| 右侧详情面板 | 400px |
| 聊天区水平内边距 | 24–32px |
| 底部输入区域 | 自适应，最小 64px |

页面采用完整窗口布局，不要让整个 App 浮在一个带巨大圆角的外部容器里。

不同区域之间只用非常轻的分割线区分。插件填满分配到的 Obsidian 工作区，不重复模拟系统窗口与标题栏。

### 笔记旁侧栏

笔记仍是工作区主体，助手在旁边单栏聊天，通讯录按需切换。关联笔记用紧凑附件或上下文提示表达，可以查看和移除，不展示整段笔记占满首屏。窄侧栏收起次要操作，不按比例缩小整套桌面界面。

### 响应式规则

断点按插件实际容器宽度判断，不只看整个窗口：

- `≥1200px`：通讯录与聊天并列，有足够空间且已实现详情时才并列详情。
- `768–1199px`：通讯录可收起；详情按需覆盖，保留关闭入口。
- `<768px`：单栏，通讯录与聊天分层切换。

不为满足三栏图强制新增头像导航轨或右面板；宿主已提供分栏能力时优先复用。

### 间距系统

采用 4px 基础网格。

常用数值：

`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48px`

不要随意使用无规律的间距。同一距离只由一层布局负责，避免内外边距重复相加。组内通常 8–12px，组间 20–24px；大留白用于组织结构，不用于把导航撑高。

## 05. 左侧 Bot Sidebar

**这是 Grok Bot 风格最重要的结构之一。**

侧边栏应以 Bot 为组织中心，而非普通聊天历史记录。

### 顶部区域

包含：

- 产品标识
- 搜索入口
- 新建 Bot / 新建聊天入口
- 侧边栏展开或收起入口

顶部控件保持简洁，以线性图标为主。

### Bot 列表

每个 Bot 展示：

- 彩色头像
- Bot 名称
- 最近一条消息或工作摘要
- 相对时间
- 未读或需要处理的状态

建议参数：

| 属性 | 推荐值 |
|---|---|
| 列表项高度 | 64px |
| 头像尺寸 | 40px |
| 列表项圆角 | 12px |
| 水平内边距 | 12px |
| 头像与文字间距 | 12px |
| 名称字号 | 14px |
| 摘要字号 | 12px |

### 状态反馈

Bot 列表至少支持：

- Idle：正常静止
- Thinking：思考中
- Working：正在工作
- Waiting：等待用户输入
- Needs Attention：需要确认
- Done：已完成
- Unread：有未读结果

不同状态映射实际运行事件，优先通过简短状态、轻微动态和简洁标记表达。不为每种状态另建一张卡，不用动画代替明确反馈。

不要在每个 Bot 后面堆放大量标签。

### 列表交互

- Hover：背景由透明变为 Surface Hover，深浅主题使用对应值。
- Selected：使用稍深的中性色底面。
- Working：头像出现低频动态。
- Needs Attention：小型提示标记。
- 右键或更多菜单：重命名、置顶、移动分组、设置、删除。
- 分组折叠、拖动排序、置顶等仅在具备对应能力后显示，不增加占位操作。
- 普通 Obsidian 文件树中的助手显示名称，隐藏 `builtin:coordinator` 等内部标识。
- 桌面通讯录以助手为中心，手机最近聊天以会话为中心；不要把同一助手的所有会话塞进桌面联系人层级。

## 06. Bot 头像设计

Grok Bot 很鲜明的特征，是一套由简洁几何形状组成的彩色角色。

### 外观规则

头像可以使用：

- 圆形
- 圆角方形
- 水滴形
- 六边形
- 云朵形
- 不规则柔和几何形

每个头像主体使用一种鲜明纯色。

例如：

`#FF2D86 / #FF6900 / #0DBBA6 / #8051F4 / #1787F7 / #19BD76`

头像中央使用两个简单的白色椭圆、短线或胶囊状眼睛。

尽量避免鼻子、嘴巴和复杂的拟人化五官。

### 视觉约束

- 默认头像库不使用照片；用户已有的自定义头像继续支持，不强制替换。
- 不使用复杂 3D 渲染。
- 不使用真实材质和复杂纹理。
- 控制在小尺寸下仍然能清楚辨识。
- 全部 Bot 保持统一的几何和眼睛语言。

### 动态状态

- Idle：默认静止；偶尔眨眼是可选设计，不为此增加常驻随机计时器。
- Thinking：眼睛轻微移动。
- Working：身体小幅摆动或旋转。
- Waiting：动作暂停，眼睛朝向一侧。
- Blocked：表情呈现疑惑。
- Done：短暂的完成反馈，然后回到 Idle。

头像是品牌体验的一部分，动效需要精致但不能喧宾夺主。标题中 20–24px、联系人中 40px 仍应可辨识；透明图片不能继承宿主的方形底板、边框或阴影。状态动画只在真实任务运行时使用，离屏暂停。

## 07. 顶部聊天标题栏

桌面内容高度约 `56px`，手机约 `52px`；系统安全区另外计算。

主要内容：

- Bot 头像
- Bot 名称
- Bot 当前状态
- 会话详情入口
- 未来实现后才出现的电脑预览相关入口

标题栏背景与主画布一致。

不使用醒目的底部分割阴影。

点击 Bot 名称或头像进入既有助手资料入口；未来实现详情面板时复用同一信息。

状态标记、标题和操作按钮需保持视觉平衡。手机保持一条紧凑导航，右侧只放最必要入口，其余进更多菜单；历史、新对话和资料不重复摆放。正常连接不常驻大横幅，未实现电脑预览时不展示相关按钮。

## 08. Chat 聊天消息系统

### 基础聊天样式

浅色主题保持大面积白色画布，深色主题使用对应 Canvas；自定义主题遵循语义映射。

Agent 消息：靠左显示。

用户消息：靠右显示。

时间信息弱化处理，不要让时间成为主要视觉元素。

### Agent 消息气泡

下列气泡、输入框与按钮的具体色值描述浅色目标；深色和自定义主题使用第 02 节对应语义，不直接保留白底黑字。

| 属性 | 推荐值 |
|---|---|
| 背景 | `#F5F5F5` |
| 文字 | `#151515` |
| 圆角 | 18px |
| 内边距 | 12px 16px |
| 最大宽度 | 主聊天区域的 76% |
| 阴影 | 默认无 |
| 边框 | 默认无 |

### 用户消息气泡

| 属性 | 推荐值 |
|---|---|
| 背景 | `#111111` |
| 文字 | `#FFFFFF` |
| 圆角 | 18px |
| 内边距 | 12px 16px |
| 最大宽度 | 主聊天区域的 76% |

### 消息间距

- 同一组消息之间：8px
- 不同轮次之间：20–24px
- 时间分隔标签上下：24px
- 消息与附件卡片之间：8px

内容需要自然流动，避免每条消息外面都套一层复杂卡片。短消息按内容收缩，最大宽度不是固定宽度；长中文、代码与窄侧栏可放宽至约 96%，不能为守比例挤成长窄列。

同一助手连续消息不逐条重复大头像、名称和模型。桌面、微信、手机等来源只在变化或需要辨识时补充，不在每条消息顶部重复整排元数据。

### 消息操作

Hover 消息时出现轻量操作：

按已实现能力提供复制、打开文件、更多操作；回复、表情反馈仅在具备能力后显示。键盘聚焦和手机更多入口同样可到达，不依赖 Hover。

不需要默认全部展开。

图片支持圆角预览，文件显示小型附件卡片。长路径能换行或展开查看。

流式内容在原气泡更新，不反复播放入场。浏览旧消息时不强制跳到底；接近底部才跟随，离开底部时提供轻量“回到最新”入口。

## 09. Composer 底部输入框

Grok Bot 的输入框应当像即时通讯软件，圆润、紧凑、可自然扩展。

### 容器

- 默认背景：`#FFFFFF`
- 圆角：24–28px
- 边框：1px 极浅灰色
- 高度：48–52px，输入多行时自适应
- 文本内边距：12–16px
- 外部水平留白：16–24px
- 最大输入高度：约 200px，并受键盘弹出后的剩余空间约束

### 左侧

圆形 `+` 按钮，添加文件、图片或其他内容。

### 中间

输入区域，占位符：

`Message [Bot Name]`

或

`向 [Bot Name] 发送消息`

### 右侧

- 语音输入入口仅在已实现时展示
- 发送按钮
- 正在生成时可切换为停止按钮

发送按钮使用黑色圆形，内置白色上箭头。

### 键盘规则

- 桌面 Enter：发送或执行；Shift+Enter：换行；中文输入法确认不提交。
- 手机 Return：默认换行，以发送按钮提交。
- Esc：返回浮层上层或关闭。
- 其他快捷键先检查 Obsidian 冲突，不直接注册参考中的 Ctrl/Cmd+B、Ctrl/Cmd+K 并覆盖宿主。
- 消息或命令提交时立即消费输入，不等待长任务结束。
- 失败仅在用户没有开始新编辑时恢复；用户期间输入、修改或主动清空的草稿不能被旧请求覆盖。
- 未填完参数的命令与技能插入保留输入，供继续编辑；控制命令不消费已有笔记附件。

输入框获得焦点时，仅做轻微边框强化，不使用发光效果。附件紧贴输入区展示并可移除；不增加常驻多排工具栏。无内容且无附件时有清楚的禁用态，生成中可以停止。

## 10. Inline Widgets 聊天内交互组件

Grok Bot 的聊天内容可以直接包含用户可操作的 UI。

这是未来扩展时应沿用的交互方式。下面是组件类型目录，不代表当前插件已经实现全部类型；不因本规范新增邮件、图表或授权流程。

### 组件类型

- 单选或多选卡片
- 邮件预览
- 待确认操作
- 文件卡片
- 工作结果卡片
- 定时任务卡片
- 工具执行事件
- 数据图表
- 简洁表单

### 卡片样式

建议：

- 卡片背景：白色或浅灰色
- 边框：1px `#E8E8E8`
- 圆角：14–16px
- 内边距：16px
- 操作项高度：44–48px
- 操作项之间通过浅色分割线区分

主操作按钮使用黑底白字，次要操作使用浅灰背景或纯文字。

### 交互要求

用户在聊天中可以直接：

- 勾选选项
- 确认或拒绝操作
- 查看任务详情
- 预览文件
- 修改计划
- 点击发送邮件

尽量不要把这些操作转换成独立的复杂后台页面。只有对应能力存在时才展示操作。普通回复不包装成结果仪表盘，卡片不层层嵌套；确认后显示真实结果，失败保留上下文，重复点击不重复提交同一动作。较长账号与权限配置仍进入设置。

## 11. 工作过程和任务状态

Bot 的工作过程采用渐进展示方式。

### 默认状态

主要显示：

- Bot 头像动态
- 简短工作状态
- 必要的进度描述

例如：

`正在搜索网页...`

`正在读取文件...`

`正在整理结果...`

### 详细状态

默认使用可展开的“工作过程 · N 步”；用户点击或用键盘展开后，才显示更多执行过程。手机不能依赖悬停。

例如：

- 已打开浏览器
- 已读取 3 份文档
- 已生成报告
- 等待授权

展示时使用小型文字行、折叠区块和弱化图标。

不要始终展开完整日志，也不要让动画或滚动日志抢占阅读空间。

### 任务完成

显示完成结果，并保留后续操作入口。

需要用户处理的问题用简洁卡片呈现。运行、取消、失败、完成分别显示，只展示可观察的真实步骤，不伪造思考过程或进度百分比。局部失败后最终成功，也保留失败步骤事实。取消说明停止后续动作，不冒充已回滚修改。

### 总管与子助手的消息流转

按照“总管发出任务 → 子助手处理 → 返回结果”融入聊天时间线：

1. 轻路由行显示发出方和接收方，可进入对应助手。
2. 任务摘要说明交给谁做什么，工具过程按需展开。
3. 子助手身份与真实进度可辨识，结果沿用同一气泡语言。
4. 保留返回总管与打开笔记入口；总管仅做必要汇总，不重复堆放相同结果块。

## 12. 右侧 Bot 详情与电脑预览

**适用边界：当前未实现的电脑预览与接管，仅保留本节作为未来设计参考。电脑负责执行任务不等于已有远程桌面，不显示无效预览或控制入口。**

### 默认行为

右侧面板默认关闭。

用户主动打开 Bot 详情或电脑预览后显示。

### 面板尺寸

推荐宽度：`380–420px`

内部包含：

- Bot 基础信息
- 运行状态
- 电脑预览
- 文件与结果
- 定时任务
- Bot 设置

### 电脑使用体验

区分三个层级：

**Status**

使用简洁状态图标说明电脑是否在运行。运行中可显示紫色。

**Preview**

右侧展开电脑预览，保持聊天区可见。

**Takeover**

用户需要操作时，将电脑预览放大至全屏或主要工作区域，并提供明确的交还控制按钮。

### 电脑预览外观

窗口背景以中性色为主。

未来确需电脑预览时使用中性窗口背景，不为了装饰增加动态壁纸或持续资源消耗。

避免默认展示过多电脑控制按钮。

## 13. 定时任务界面

产品统一称“定时任务”，不混用多个栏目。任务属于助手的长期能力，与负责的助手关联，由聊天创建、修改时间与内容。

### 列表项

展示：

- 任务名称及负责助手
- 执行时间或触发条件
- 启用状态
- 最近执行结果

### 视觉参数

- 卡片圆角：14px
- 卡片间距：8–12px
- 内边距：16px
- 标题字号：14px
- 描述字号：12px

设置中支持查看、暂停/恢复、取消和管理通知渠道；编辑任务内容由聊天完成，不新增手动创建表单。通知渠道集中配置，任务只选择渠道，不重复填写账号。

定时任务执行时，相关事件可以出现在所属助手的聊天时间线中。服务已接收、任务已执行和手机实际送达是不同状态，不能互相替代。

## 14. 按钮、圆角与阴影系统

### 圆角 Token

| 类型 | 值 |
|---|---|
| 小型按钮 | 8px |
| 普通菜单项 | 10px |
| 侧边栏列表项 | 12px |
| 普通卡片 | 14px |
| 消息气泡 | 18px |
| 输入框 | 26px |
| 胶囊按钮 | 999px |

### 按钮

Primary：黑色背景、白色文字。

Secondary：浅灰背景、深色文字。

Ghost：透明背景，悬停时出现浅灰底色。

Destructive：危险操作使用红色文字。每组只有一个主操作；Default、Hover、Pressed、Focus、Selected、Disabled、Loading 状态有各自含义，反馈不能改变点击范围。深色通过表面和细边界分层，不堆厚阴影。

### 阴影

常规消息气泡不使用阴影。

悬浮按钮和弹层可以使用：

`0 4px 20px rgba(0,0,0,0.04)`

悬浮面板可以使用：

`0 12px 32px rgba(0,0,0,0.08)`

禁止使用明显的蓝色外发光、厚重投影或拟物高光。

## 15. 图标系统

推荐使用 Lucide 风格的线性图标。

建议规格：

- 图标尺寸：16 / 18 / 20 / 24px
- 描边宽度：1.75–2px
- 描边端点：Round
- 默认颜色：`#424242`
- 次要颜色：`#A0A0A0`

统一使用简洁的轮廓图标。

不要在同一个界面混用三种不同图标库。

图标按钮建议最小可点击范围为 40px；移动端至少 44px，图形本身通常 20px，不因此变成巨型按钮。复用 Obsidian 的 Lucide 风格图标，纯图标提供可访问名称，陌生动作配短文案。

## 16. 交互动效规范

整体动效遵循轻、短、自然的原则。

| 场景 | 时间 | 推荐曲线 |
|---|---|---|
| 按钮悬停 | 120ms | ease-out |
| 列表选中 | 160ms | ease-out |
| 弹出菜单 | 180ms | ease-out |
| 侧边栏展开 | 220ms | ease-in-out |
| 右侧面板展开 | 240ms | ease-in-out |
| 消息进入 | 180ms | ease-out |
| 头像状态切换 | 250ms | ease-in-out |

### 细节限制

- 禁止大幅度弹跳。
- 禁止频繁的缩放和旋转。
- Hover 不需要每次都放大按钮。
- 消息进入时最多使用 4–8px 的轻微位移。
- 工作中头像动效应低频、平滑。
- 支持 `prefers-reduced-motion`。

交互反馈要让用户感觉界面很灵敏，但不能让人意识到每个控件都在刻意表演。

既有紧凑菜单的 110ms 入场、按钮 90–130ms 反馈可继续沿用，不为统一表格而强制变慢。流式片段不重播动画；工作循环与真实运行状态关联，空闲无持续呼吸。减少动态效果模式移除非必要位移、缩放与循环，不影响操作。设置页不加整页入场秀，动画不阻塞发送和取消。

## 17. Mobile 移动端设计

移动端保留桌面版的基础视觉语言，按 CSS 像素与实际可用宽度布局，不照搬参考图片物理尺寸。

### 通讯录首页

参考用户的 Grok Bot 手机图：顶部左侧个人/设置入口，右侧搜索与新增；下方常用助手头像区，再下方最近聊天。按现有能力映射入口，不伪造个人账号系统。

| 元素 | 目标 |
|---|---|
| 顶部导航内容高度 | 约 52px，不含系统安全区 |
| 按钮点击范围 / 图标 | 44px / 20px |
| 常用助手头像 | 52–68px，按容器自适应，通常最多三列 |
| 最近聊天头像 / 行高 | 40px / 约 64px |
| 页面左右边距 | 16–20px |

助手少时自然排列，不拉伸成巨型头像。名称、摘要和时间形成层级，不能被宿主强调色统一染成亮色。

### 顶部导航

- 左侧：返回按钮
- 中间或偏左：Bot 头像及名称
- 右侧：当前必要入口或更多操作，电脑预览仅在未来实现后出现

导航按钮使用圆形或胶囊形浅色容器。

### 聊天区

- 背景：近白色
- 左右边距：16–20px
- 消息最大宽度：约 82–88%
- 消息正文：15–16px，现有紧凑正文可保留 15px；输入文字保持 16px
- 消息气泡圆角：18px

### 底部输入框

采用贴近屏幕底部的悬浮胶囊式布局。

左侧为独立 `+` 按钮，右侧为语音或发送按钮。

必须适配键盘弹出、安全区域和输入框多行增长。

### Bot 列表

移动端使用独立列表页面，不强制展示永久侧边栏。

优先保留头像、名称、最近工作摘要和状态。手机聊天使用一条紧凑导航，不堆两排工具栏；正常连接状态收进相关入口，异常时在当前区域提供说明与重连。

### Obsidian、状态栏与键盘

- 仅在插件视图激活时隐藏宿主导航、工具栏等占位，释放空间交给插件；离开后恢复，不影响其他笔记。
- 顶部布局为“系统安全区 + 52px 导航内容 + 滚动内容”；安全区来自系统或宿主有效值，只计算一次，不叠加两份 inset，不按手机型号写固定偏移。
- 顶部按钮避开状态栏，底部输入避开手势区。隐藏宿主后不残留原占位空白。
- 键盘弹出后跟随可视区域约束输入与浮层高度；发送按钮不落到键盘下，菜单不覆盖导航。
- 旋转、横向安全区、前后台恢复同样适配，不用固定屏幕高度锁死布局。
- 手机负责交互、电脑执行。“电脑已接收”不能冒充“任务已完成”；断线恢复保留操作身份，不引导重复执行。

## 18. 空白页与新建 Bot

新建 Bot 页面尽量减少表单感。

初始界面可以只包含：

- 一个醒目的 Bot 头像
- 一句简洁的欢迎标题
- 一段简短描述
- 一个主要操作按钮
- 少量建议选项

页面使用大量留白，视觉焦点集中在头像和操作按钮。

不需要展示大量配置字段。

创建 Bot 后，更多名称、描述、权限、工具和设置可以逐步提供。先收集名称、负责文件夹、职责等必要信息；高级配置沿用资料编辑器，界面简化不能悄悄改变权限默认值。

总管通过聊天创建助手时，成功给出打开入口，失败显示真实原因。首次未连接、电脑离线、空聊天和无搜索结果分别说明下一步，不统一显示“暂无内容”。

## 19. 性能与体验约束

视觉设计必须兼顾响应速度。

- 侧边栏切换应尽量即时。
- 输入框在页面加载后应尽早可用。
- 长聊天先分页；列表规模确有需要时再虚拟化，并保留焦点、滚动锚点与可访问性。
- 复杂聊天卡片按需加载。
- 聊天滚动不应因为新消息出现而突然跳动。
- 右侧面板展开不得破坏当前滚动位置。
- 工作状态只更新相关组件，避免整页重绘。
- 加载状态保持低干扰。
- 所有重要操作保留键盘支持和可见焦点。
- 流式正文复用节点并合并更新，不随每个片段重建 Markdown 组件。
- 每次输入不扫描全库、不重新连接 MCP、不重复请求模型目录。
- 视图关闭释放监听器、计时器与渲染组件，空闲界面无无效高频任务。
- 通过缓存、复用、局部刷新降低消耗，不删功能、降低视觉质量或省略必要反馈。

### 视觉

- [ ] 以黑白灰和留白为核心
- [ ] 没有多余渐变、彩色背景和厚阴影
- [ ] 头像采用统一的彩色几何语言
- [ ] 消息气泡、输入框、菜单具有统一圆润风格
- [ ] 文字大小、字重、行高一致

### 结构

- [ ] 左侧以 Bot 名单为中心
- [ ] 中央为主要聊天画布
- [ ] 已有详情入口按需打开，不占用默认聊天空间
- [ ] 未实现的预览、接管、邮件等没有无效入口
- [ ] 实际具备的文件、结果与任务组件沿用聊天内样式

### 交互

- [ ] Hover、Focus、Active、Disabled 状态完整
- [ ] 状态变化具有轻微动效
- [ ] Bot 工作状态清晰
- [ ] 操作可撤销或可确认的场景具有反馈
- [ ] 侧边栏和弹层支持键盘操作
- [ ] 移动端导航、安全区、键盘与宿主恢复正确，无遮挡和占位空白

### 一致性

所有页面必须使用相同的 Design Tokens。

不允许某个页面突然换成传统 Dashboard 风格。

不允许为了突出功能而加入大量彩色按钮、复杂图表和装饰性容器。

**最终目标：打开应用后，用户应当立即感受到 Grok Bot 式的简洁、圆润、克制和即时通讯体验。功能可以复杂，界面必须保持轻盈。**

## 21. 设置页设计

设置沿用同一中性、圆润和留白语言，优先原生 `Setting` 行与已有分组，不改成仪表盘。

| 分类 | 内容边界 |
|---|---|
| 助手 | 名称、头像、职责、提示词、模型继承/覆盖、独立权限 |
| 模型与账号 | 全局模型来源、订阅/API 账号、可用模型 |
| 技能与工具 | Skills 位置、MCP 配置、实际能力状态 |
| 连接 | 微信、手机连接、设备管理 |
| 定时任务 | 任务列表、运行控制、通知渠道 |
| 通用 | 通用偏好及已有维护选项 |

### 视觉与排版

- 标题—说明—控件保持稳定对齐。字段名约 14px，说明 12–13px；分组间约 24px，行内 12–16px。
- 窄屏控件移至下一行，不挤压说明或撑出横向滚动；长说明按需展开，不用小字塞满。
- 先展示常用项，高级项折叠；同一字段不在多个分类重复配置。
- 主次按钮、下拉、开关、状态提示使用同一语法；普通成功使用轻反馈，不再要求点“确定”。

### 配置语义

- 全局默认与当前会话/单助手覆盖明确区分；切换账号来源后，继承默认的助手跟随，不要求逐个调整。
- 权限按“能做什么、能访问哪里”解释，复用同一权限组件，不因文案简化扩大权限。
- 定时任务由聊天创建和改内容；设置用于查看、暂停、取消与渠道管理。
- 账号与渠道集中管理，密钥不作为普通说明文字展示。
- “已登录”“有权限”“调用成功”“已提交”“已完成”依真实结果分别显示，未调用不标为已验证。
- 保存失败保留输入并在当前区域解释，不跳到另一个配置窗口。

## 22. 斜杠命令与轻浮层

交互遵循主流 agent 的输入区命令逻辑，视觉沿用本文的 Grok Bot 风格。

1. 输入 `/`，菜单锚定输入框上方；命令 → 参数 → 帮助或短状态沿用同一浮层。
2. 方向键选择，Enter 执行，Tab 只补全，Esc 返回上层或关闭；触控点选语义一致。
3. 模型与思考级别选中即应用，显示真实当前值，不再弹第二个窗口，不要求重新发送参数。
4. 技能插入后继续输入任务；`/name` 等参数在原输入框填写。模型快捷入口不覆盖普通草稿。
5. 加载、空结果、错误原位呈现；关闭或切换会话后，迟到结果不能重新打开浮层或应用到别的会话。

浮层使用 Canvas、轻边界、14–16px 圆角与柔和阴影，操作行目标至少 44px。可用高度限制在输入区和导航之间，内部可滚动，不遮导航、不越出视口、不随每个字符更换容器。

| 用户意图 | 容器 |
|---|---|
| 临时选择、命令帮助、短状态 | 输入区浮层或既有轻菜单 |
| 单次成功反馈 | 轻提示或当前消息状态 |
| 错误及重试信息 | 当前操作附近，保留上下文 |
| 完整账号、权限、连接配置 | 既有设置页或助手资料编辑器 |
| 较长表单 | 复用编辑容器，失败保留输入 |
| 需要真实决定的高影响动作 | 既有确认模式，清楚说明影响 |

普通新功能不默认使用居中大弹窗，可逆操作不层层确认。
